# 구조와 구현 계약

## 두 직무 분야, 하나의 엔진

`domains.ts`가 백엔드·데이터 분야의 역할, 예시 조건, 매칭 안내 규칙을 지정합니다.
두 페이지는 같은 채팅 UI와 API를 사용하지만 대화 상태와 서버 공고는 분야별로 분리합니다.
분야는 API가 검증합니다. 모델이 임의 분야나 파일 경로를 지정할 수 없습니다.

## 세 단계 파이프라인

- 수집: 채용 페이지·메일을 정형 공고 데이터(JSON)로 가져옵니다. 현재는 Python 수집 + 사람 검토.
- 매칭·평가: 공고를 검색·읽어 이력서와 비교하고 강점·보완점을 설명합니다. 현재는 규칙 기반 데모.
- 리포트·액션: 매칭 결과와 출처를 반환합니다. 알림·자소서 초안은 이후 확장 대상입니다.

## 경계

- 브라우저: 채팅 입력, 최근 대화, 매칭 설명과 출처 및 완료된 활동 기록.
- Next.js 서버: 공고 파일 읽기, 도구 실행, 제공자 선택과 추후 비밀키 사용.
- Python: 별도로 실행하는 공고 수집·검토 승인 명령. 사용자 질문 때 실행하지 않습니다.

## POST /api/chat

입력: `{domain: "backend" | "data", messages: [{role: "user" | "assistant", content: string}]}`.
최대 12개, user부터 교대로 시작하고 user로 끝납니다. 메시지는 1~2000자입니다.
전체 요청은 30000자까지 허용합니다. user/assistant 텍스트만 전달하며 UI 출처나 실행 기록은 요청에 섞지 않습니다.

출력: `{mode: "demo", answer, citations, activities}`.
출처는 실제 도구로 읽은 공고 ID에 한해서 서버가 구성합니다.
잘못된 입력은 400, 큰 요청은 413, 공고/제공자 설정 오류는 503입니다.
도구 실패나 제공자 실행 실패는 답변에 확인 불가와 실행 오류 기록을 반환합니다.

## 실행 흐름

제공자에 역할 규칙·메시지·도구 정의·누적 도구 결과를 전달합니다.
도구 요청이면 이름과 인자를 검증한 뒤 실행하고, `callId`와 함께 결과를 제공합니다.
답변이면 읽은 공고에서 출처를 구성합니다. 질문당 도구는 최대 3회입니다.
`read_source`는 해당 요청의 검색 결과에 포함된 ID만 허용합니다.
도구 오류는 제공자에 결과로 전달합니다. 무한 반복은 호출 한도로 막습니다.

## 공고 저장소

`SourceRepository.list(domain)`을 서버에서 구현합니다. 현재는 data/<domain>.json입니다.
앱은 파일을 요청 때 읽으므로 검토 승인한 공고는 다음 요청부터 사용됩니다.
파일별 공고 ID는 고유하게 유지합니다. 검토 여부와 메타데이터를 검증해 잘못된 항목을 제외합니다.
이후 DB/서버를 사용하면 저장소 구현만 교체하고 검색/읽기 도구 계약은 유지합니다.

## 추후 실제 모델

실제 모델 어댑터는 tools 스키마를 제공자의 함수 호출 형식으로 변환하고,
이전 요청/도구 결과의 연결을 유지합니다. 누적 결과에서 대화 메시지를 재구성할 때 중복 삽입하지 않습니다.
공고 본문은 신뢰할 수 없는 외부 콘텐츠로 취급하고, 본문에 있는 지시를 시스템 지시로 승격하지 않습니다.
매칭 점수 계산과 이력서 벡터화(RAG)는 이 단계에서 붙입니다. 현재 인터페이스는 단순한 순차 도구 호출 실습용입니다.

## 내부 안내 경로

/admin은 공개 메뉴와 페이지에서 연결하지 않는 읽기 전용 구현 가이드입니다.
robots 메타데이터는 noindex/nofollow이며, /study는 기존 주소 호환용으로 /admin에 이동합니다.
현재 인증은 없습니다. 공개 배포 전 서버 측 관리자 인증·권한 검사를 추가합니다.
