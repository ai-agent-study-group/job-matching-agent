화면 4개의 흐름, 화면마다 필요한 값, 누르는 것마다 부르는 API를 적는다. API 설계(#69 · #70 · #74)의 입력으로 쓴다.

- 기준 코드: `src/domain/profile.py` · `src/domain/criteria.py` · `src/domain/job.py`, `web/lib/api-types/api.generated.ts`
- 아직 없는 모양: `Conditions` · `SearchRequest`(#79), `MatchResult` · `Check`(#81 초안)
- 표시: ✅ 지금 있음 · 🟡 티켓에 초안만 있음 · ❌ 없음, 정해야 함

## #61 "FE와 맞출 것"에 대한 답

- 화면에 보여 줄 값: 프로필 보기에 필요한 값은 다 있음. 이름 · 연락처 제외도 동의. 직무별 경력 기간(`role_months`)은 있으면 강점으로 보여 줄 수 있어 찬성(필수는 아님)
- 코드값 → 화면 이름 표: FE가 가짐. `web/domain/profile/labels.ts`(경력 수준 · 언어 수준 · 언어 코드), 매칭은 `web/domain/match/labels.ts`. 표에 없는 코드는 원래 값 그대로 보여 줌
- 날짜 두 형식: 처리함. `"2023-01"` → `2023.01`, `"2020"` → `2020`, `end`가 null이면 "재직 중"(학력은 "재학 중")

## 정할 것 (BE · LLM에 물을 것)

1. **매칭 실행 방식(#74)**: 검색 뒤 매칭을 FE가 공고마다 따로 부르나, `/api/search`가 매칭까지 해서 주나, 작업 ID로 시작하고 조회하나. 공고 N개 × LLM 호출이라 한 요청이면 오래 걸림 → 결과 목록의 로딩 화면 모양이 여기에 달림
2. **매칭 응답에 공고 요약을 같이 줄지**: `MatchResult`에는 `source` · `posting_id`만 있음. 화면은 회사 · 직무명 · 근무지가 같이 필요
3. **점수 범위**: `score`가 0~1인지 0~100인지. FE는 지금 0~1로 보고 %로 바꿈
4. **목록의 원문 링크**: 검색 결과의 `url`이 비어 있음. 목록에서 원문으로 가려면 채워 주거나, 공고 하나 가져오는 API가 필요
5. **프로필 보관(#74)**: FE가 들고 있으면 새로 고침하면 사라짐. 세션 저장(`sessionStorage`)으로 버틸지, 서버 저장(`profile_id`, DB · 로그인)까지 갈지
6. **파일 업로드**: `/api/profile` 라우트가 아직 파일을 415로 막음(#103 파서가 merge됐지만 라우트에 연결 안 됨). FE는 파일을 보내고 있음
