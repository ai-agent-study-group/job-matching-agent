# QA 설계 (추후)

[현재 구조와 기술](../STRUCTURE.md) · 영역별 설계: [BE](be.md) · [LLM](llm.md) · [FE](fe.md) · [DevOps](devops.md) · **QA**

## 1. 평가 셋

JMA 앱의 매칭 agent는 기준이 고정돼 평가 셋으로 잴 수 있어서(LLM-4), 평가 셋은 1차 안건에 남김.

- **지금 계획:** `eval/` README에 "실제 공고 약 30개 + 지원할 만한가 정답 라벨", 담당 LLM2·PO로 적혀 있음
- **기준 이력서:** 누구 이력서로 라벨을 달지 정함. 실제 이력서는 공개 저장소에 올릴 수 없음
- **공고 본문 보관:** 공고는 마감되면 내려가서, 본문을 따로 저장해야 같은 평가를 다시 돌릴 수 있음. 저장 위치는 사이트 이용 조건과 같이 봄
- **라벨 형식:** 지원/보류 같은 범주로 할지, 점수(0~100)로 할지. agent 점수와 어떻게 비교할지도 같이 정함
- **쓰는 곳:** 기본 모델 고르기(LLM-5), 프롬프트를 고치기 전후 비교

| 정할 것 | 선택지 | 참고 | 결정 |
| --- | --- | --- | --- |
| 평가 셋 이력서 | 가짜 이력서 / 팀원 이력서 (비공개 보관) | 공개 저장소 |   |
| 라벨 형식 | 범주 / 점수 | BE-3 MatchResult(점수) |   |
| 만드는 시점 | 1차 안 / 1차 이후 | 기본 모델을 정하려면 필요 |   |

## 2. 테스트 방식

LLM이 들어가면 같은 입력에도 결과가 달라질 수 있음. 그래서 코드가 맞는지 보는 테스트와 매칭 품질을 보는 평가를 나눔. 1차에는 MCP 도구 목록 확인을 더함.

![테스트별 범위 · 가짜로 바꾸는 부분](../assets/structure/qa-scope.svg)
*테스트별 범위 · 가짜로 바꾸는 부분*

| 종류 | 확인하는 것 | LLM·네트워크 | 언제 |
| --- | --- | --- | --- |
| 단위 테스트 | 코드 단계: 1차 거르기 규칙, 중복 제거, 정렬, 점수 합산 | 없음 | PR마다 CI |
| 어댑터 테스트 | 사이트 응답 → 공고 변환. 저장해 둔 응답 파일로 확인 | 없음 | PR마다 CI |
| 흐름 테스트 | MCP 도구 · API를 불러 흐름이 끝까지 돌고 출력이 스키마에 맞는지. pydantic-ai는 `TestModel`을 제공함 | 가짜 LLM | PR마다 CI |
| MCP 도구 목록 확인 | 도구 이름 · 설명 · 입력 형식이 바뀌지 않았는지 | 없음 | PR마다 CI |
| 사이트 형식 확인 | 실제 사이트 API 응답 형식이 바뀌었는지 | 네트워크 | 추후 (정기 실행) |
| 품질 평가 (QA-1) | 정답 라벨과 매칭 결과 비교 | 실제 LLM·키, 비용 있음 | 수동 또는 정기 |
| E2E | FE → API → 결과까지 | 선택 | 추후 |

| 정할 것 | 선택지 | 참고 | 결정 |
| --- | --- | --- | --- |
| CI에서 실제 LLM 호출 | 안 함(가짜 LLM만) / 일부 테스트만 | 키·비용. LLM-5 |   |
| 저장해 둔 사이트 응답 | 저장소에 올림 / 비공개로 보관 | 사이트 이용 조건(DevOps-6) |   |
| 품질 평가 | 실행 주기와 기준, PR 병합 조건으로 쓸지 | QA-1 |   |
| web 테스트 | CI에 넣음 / 안 넣음 | 메인-2 ③ CI 검사 범위 |   |
