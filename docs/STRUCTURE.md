# 현재 코드 구조와 연결

등록한 채용 사이트에서 공고를 검색·추출한 뒤, 미리 등록한 이력과 요건별로 매칭하는 프로젝트입니다. JD는 Job Description(직무 기술서)을 뜻합니다.

## 기능 흐름

사이트 목록 설정 → 이력 직접 등록 → 공고 검색·추출 → 비교·매칭 → 평가 → 웹에서 결과와 근거 확인.

PoC에서는 매칭 agent가 공고 원문을 읽습니다. Gmail 알림 수집은 PoC에서 제외하며, 이력서 업로드·파싱과 대화 보충은 추후 범위입니다. 공고를 JD 스키마로 먼저 구조화할지는 추후 결정합니다.

[10월 20일 안건](meetings/2026-10-20.md)의 스키마, 역할 구분과 코드 위치는 회의에서 확정합니다.

## 코드와 문서 위치

| 경로 | 내용 | 담당 상태 |
| --- | --- | --- |
| `src/domain/` | 모든 층이 같이 쓰는 데이터 형식 (Profile · SearchQuery · JobPosting · JD · MatchResult) | 전원 합의 |
| `src/port/` | 코어와 어댑터 사이 약속. `inbound` = 유즈케이스, `outbound` = 공고 출처 · 저장소 | 역할 구분 후 배정 |
| `src/service/` | 유즈케이스 구현 · 도구 / 서비스 로직 | 역할 구분 후 배정 |
| `src/adapter/inbound/` | `api`(FE용 /api) · `mcp`(MCP 서버) · `agent`(pydantic-ai) | 역할 구분 후 배정 |
| `src/adapter/outbound/` | 공고 출처(Greenhouse · 연방고용청 API, 스크래퍼는 추후) · 저장소(추후) | 역할 구분 후 배정 |
| `src/main.py` | 조립: 어댑터를 service에 연결하고 /api와 /mcp를 한 앱에 올림 | 역할 구분 후 배정 |
| `test/` | `src/`와 같은 구조의 백엔드 테스트 | 각 담당 |
| `web/` | 사이트 목록 설정, 이력 등록, 결과·근거 확인 화면 | 역할 구분 후 배정 |
| `eval/` | 평가셋과 정답 라벨 | 역할 구분 후 배정 |
| `infra/` | 배포와 CI | 역할 구분 후 배정 |
| `docs/` | 직군별 메모, 공통 안내와 회의 기록 | 전원 |
| `scripts/preview-docs.mjs` | 문서 로컬 미리보기 | 문서 도구 |

백엔드는 루트의 `pyproject.toml`로 관리하는 Python 프로젝트입니다. 실행 프로세스와 작업 전달 방식은 회의에서 정합니다.
현재 구현된 API는 `/health`이며 다른 모듈과 `web/`은 작업을 시작할 공간입니다. 위 표는 각 모듈의 구현 범위를 안내합니다.
`src/`는 헥사고날(포트 · 어댑터) 구조입니다. 바깥 층이 안쪽을 import하고, 도메인은 아무것도 import하지 않습니다.

## 함께 정할 연결 지점

| 연결 | 정할 내용 |
| --- | --- |
| 사이트 목록 ↔ 검색 도구 | 목록 등록 주체·형식, 공고 식별자, 중복 기준, 재시도와 실패 처리 |
| 공고 소스 어댑터 ↔ agent | 공고 원문, 출처 URL, MCP 도구 계약 |
| 이력 등록 ↔ agent | 직접 등록 형식, 경력 항목과 기술·언어 필드 |
| 언어 모델 ↔ API | 요건별 충족 여부, 근거 출처, 점수와 오류 형식 |
| API ↔ 웹 | 공고·이력·매칭 결과의 요청과 응답 |
| 구현 ↔ 평가 | 평가셋, 정답 라벨, 점수와 회귀 확인 |

실행 방법은 [저장소 소개](https://github.com/ai-agent-study-group/job-matching-agent#readme), 작업 기록은 직군별 폴더에서 확인합니다.
