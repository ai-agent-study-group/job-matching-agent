# 현재 구조와 연결 논의

이 문서는 복사된 저장소의 현재 상태와 연결할 지점을 설명합니다. 문서에 폴더가 있다고 기능이 완성된 것은 아닙니다.

## 현재 확인된 코드

- 루트 `pyproject.toml`: Python 3.12 이상, FastAPI·uvicorn 의존성, uv 프로젝트 설정.
- `src/api/main.py`: `/health` API와 대응 테스트가 있는 기본 서버.
- `src/ingest`, `src/scraper`, `src/llm`, `src/schemas`: 역할 README와 패키지 초기 파일.
- `web/`: 법률 데모의 UI·구조를 재사용해 이력서 매칭 도메인으로 바꾼 Next.js/TypeScript 규칙 기반 데모.
- 웹 예시 공고는 사람이 작성한 예시이며 실제 AI 호출이나 완성된 이력서–JD 매칭을 의미하지 않습니다.
- 문서 사이트는 `docs/index.html` 한 파일로 화면·메뉴·역할별 읽기 안내를 구성합니다.

## 현재 폴더와 작업 경계

| 경로 | 현재 설명·역할 후보 | 추가로 정할 것 |
| --- | --- | --- |
| `src/ingest/` | 알림·수집 실행·스케줄링 계획 | 사이트 수집과 메일 입력의 우선순위 |
| `src/scraper/` | 사이트/ATS별 JD 수집 계획 | 첫 사이트, 수집 방식·주기 |
| `src/llm/` | JD 구조화·이력 비교·점수 계획 | 모델, 이력서 파싱 위치, agent 동작 |
| `src/api/` | FastAPI 기본 서버 | 업로드·프로필·작업·공고·결과 API |
| `src/schemas/` | 공통 데이터 형식 계획 | 이력서·JD·매칭·오류 스키마 |
| `web/` | 현재 학습용 웹·API·agent 데모 | Python API 연결과 임시 서버 코드 정리 |
| `tests/` | 현재 health 테스트 | 기능·연결·오류 테스트 범위 |
| `eval/` | 매칭 평가 계획 | 사례·기대 결과·평가 형식 |
| `infra/` | 운영 설정 계획 | 배포·작업 실행·저장·관측 |

## Phase 1 연결 흐름 후보

```text
이력서 업로드 → 정보 추출·구조화 ─┐
                                 ├→ 요건별 비교·점수 → 추천 공고 목록
채용 사이트 → JD 수집·구조화 ────┘
```

이 흐름은 회의 범위를 이해하기 위한 그림이며 프로세스·서버 분리를 확정한 것은 아닙니다.

| 연결 | 합의할 질문 | 결정 |
| --- | --- | --- |
| 웹 ↔ API | 파일 업로드, 추출 확인, 처리 상태, 결과 조회 형식은? | ? |
| API ↔ 파싱/매칭 | 동기 응답인가, 백그라운드 작업과 상태 조회인가? | ? |
| 수집 ↔ 저장 | 공고 고유 ID·중복·변경·수집 시점은 어떻게 기록할까? | ? |
| 데이터 ↔ LLM | 이력서·JD 구조와 비교 결과의 공통 형식은? | ? |
| 매칭 ↔ 화면 | 점수·충족/부족/정보 없음·근거를 어떻게 전달할까? | ? |
| 운영 | DB·작업 전달·모델 제공자·배포는 무엇으로 할까? | ? |

기존 Python API 구조를 어떻게 발전시킬지는 논의가 필요합니다.
모델 제공자·저장소·프로세스 구성과 각 모듈의 세부 구현은 별도로 결정해야 합니다.
